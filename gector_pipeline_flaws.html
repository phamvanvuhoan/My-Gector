Critical bugs
Variable shadowing in _predict() inner loop
src/gector/predict.py — _predict(), line ~50
The outer loop variable i (iterating over batches: for i in itr) is re-used as the inner loop variable for i in range(len(outputs.pred_labels)). After the inner loop completes, i holds the last inner index (e.g. 127 for batch_size=128), so the next batch starts at srcs[128:256] — which happens to be correct only for batch_size=128. For any other batch size, slicing is off. Rename the inner variable to j.
d_labels masking overwrites labels, not d_labels
src/gector/modeling.py — forward(), ~line 110
d_labels[labels == -100] = -100 is set after labels[labels == pad_id] = -100, which is correct. But immediately before the detection loss, there's no guard: if a pad position is only in d_labels (e.g. due to a length mismatch), those positions propagate into the detection loss. This is a subtle masking inconsistency that silently inflates loss_d on pad tokens.
Loss weight tensor device mismatch on multi-GPU
src/gector/modeling.py — forward(), ~line 116
The fix self.loss_fn.weight = self.loss_fn.weight.to(logits_labels.device) is done inside forward() on every single call. This is both inefficient and not thread-safe under DDP — each process copies the tensor to its own device, but mutates the shared loss_fn object in place. The weight should be moved once during model initialization or in to(device), not patched every forward pass.
LR scheduler built on incorrect warm_epochs
train.py — main(), ~line 175
warm_epochs = max(0, args.n_epochs - max(args.n_cold_epochs, resume_epoch)) uses resume_epoch at construction time, but if the job resumes mid-training (e.g. epoch 0 of a 10-epoch run), this shrinks num_training_steps relative to what the original run used. The scheduler sees fewer total steps and miscalibrates its decay, causing the LR to drop faster than intended on cosine schedules. The scheduler should always be built for the full warm steps regardless of resume position.
Logic / correctness warnings
shuffle=False when resuming kills data randomness
train.py — _make_dataloader(), ~line 205
shuffle = skip_n == 0 means any resumed epoch trains on a deterministic, ordered slice of the dataset. This biases gradient updates toward examples that happen to appear late in the file order, typically harder or domain-specific examples. A better approach: shuffle with a seeded generator and fast-forward by skip_n steps, or just always shuffle and accept a small overlap on resume.
SkipDataset.reset() is called a step too late
train.py — training loop, ~line 248
resumed_train_dataset.reset() is called at the top of the epoch loop with condition if epoch > resume_epoch. Since train_loader wraps the dataset and was created before the loop, the DataLoader's sampler already saw the initial (possibly skipped) length at construction. Calling reset() mid-run changes __len__ but doesn't rebuild the sampler, so the epoch after resume still draws from the skip-adjusted view.
Scheduler fast-forward only runs if resume_step > 0
train.py — ~line 234
If a checkpoint was saved exactly at the end of an epoch (resume_step == 0), the scheduler is never fast-forwarded even though resume_epoch * steps_per_ep steps have already been taken. The condition should be if global_step > 0, not if resume_step > 0.
Class weight computation runs over train_dataset, not resumed_train_dataset
train.py — ~line 155
compute_class_weights(train_dataset, ...) is called on the full unsliced dataset, which is correct for computing representative weights. However, this is also a very slow pass over potentially 8M rows that re-runs on every preemption restart. The weights should be cached to disk alongside the vocab so restarts skip it entirely.
Beam search applies no_correction_ids as a list, not a set
src/gector/beam_predict.py — _score_hypotheses(), ~line 40
no_correction_ids is built as a set in beam_predict() but passed to _score_hypotheses() as list(no_correction_ids), then checked with in no_correction_ids inside the function which receives a list. The membership test is O(n) instead of O(1). With thousands of label positions this is measurable. Pass the set directly or keep it as a set inside the helper.
word_masks passed but not used in beam's _score_hypotheses
src/gector/beam_predict.py — ~line 75
The function computes word_masks via get_word_masks_from_word_ids and then uses wm for the max error probability gate. But the word_positions list is built from wm[j].item() == 1 inside a list comprehension that also checks if batch.get('attention_mask', None) is not None — a condition that is always true since the batch always has an attention mask. This dead branch adds confusion without filtering anything.
Design / robustness notes
preprocess_all does not commit after each file on failure
modal_train.py — preprocess_all()
volume.commit() is called after each file's build_cache() returns, but only if build_cache itself doesn't raise. If tokenization crashes mid-file (OOM, malformed line), no commit happens and the partial mmap is lost on preemption. The build_cache internal 5-batch commits survive, but the Modal volume state won't reflect them until the next successful commit call.
has_args_add_pooling instantiates the full model just to inspect a signature
src/gector/utils.py
AutoModel.from_config(...).__class__.__init__ calls AutoModel.from_config which instantiates (on CPU) the entire transformer just to read its __init__ signature. This wastes several seconds and allocates a large temporary model. Use inspect.signature(AutoModel._model_type_to_module[...] or AutoConfig) or simply hard-code the list of models that do/don't support add_pooling_layer.
vocab.py's build_vocab calls non-existent get_labels_freq()
src/gector/vocab.py — build_vocab()
train_dataset.get_labels_freq(...) is called but GECToRDataset has no such method. This function will crash at runtime if ever called. It appears to be a leftover from an older dataset API. Either implement the method or remove build_vocab since the codebase exclusively uses load_vocab_from_official in practice.
No gradient clipping anywhere in the training loop
train.py — train_epoch()
The optimizer step has no clip_grad_norm_ call. For large RoBERTa/XLNet models fine-tuned on noisy GEC data, gradient explosions are common during warm-up. The original GECToR paper and most transformer fine-tuning recipes clip at 1.0. Add accelerator.clip_grad_norm_(model.parameters(), 1.0) before optimizer.step().
Cold epoch LR override can fight loaded checkpoint LR
train.py — training loop, ~line 245
When resuming into a warm epoch, the code checks if optimizer.param_groups[0]['lr'] == args.cold_lr to decide whether to reset LR. But accelerator.load_state restores the optimizer state (including LR) from the checkpoint. If the last checkpoint happened to be saved during a cold epoch of a previous run, this heuristic silently leaves the wrong LR in place. The phase (cold/warm) should be derived from epoch index alone, not from the optimizer state.
